# Stage 1 required-check recovery policy proposal

**Status:** Proposal for maintainer review only. No policy or permission change is authorized.

## Current policy evidence

The canonical `risk-rules.yml` has only `low`, `medium`, `high`, and `criticalActions`; its six known actions include `branch_protection_bypass`. `policy.mjs` enforces exact schema keys, requires that fixed critical-action set, and rejects unknown action IDs. `classify-risk.mjs` rejects any action outside that set and makes every accepted action critical. The protected-path policy classifies `.agent/policy/**`, `.github/workflows/**`, and `scripts/loop/**` as high; the stop policy sets `ciRunLimit: 2`. The Loop Engineering contract says critical actions remain non-executable, high-risk work requires trusted exact-scope approval, and policy changes must be reviewed and merged before a fresh implementation run.

The design and plan propose a trusted `main` workflow that verifies exactly one allowlisted `client` or `server` check definition against the exact current PR SHA, then uses a separate publisher to update the unique original failed Check Run. The existing required context and App identity are retained (Actions App ID `15368`). This is not a neutral report: after independent verification, it intentionally changes the existing required failure to success.

## Recommendation: propose a separate, narrowly bounded high-risk action

Recommend policy review of a distinct action, `stage1_required_check_recovery`, covering both the exact trusted dispatch and the later Check Run update. This classification is justified only if maintainers define `branch_protection_bypass` as bypassing the protected validation without independently rerunning that exact validation. The operation still changes the outcome used by branch protection and must remain high risk, human approved, disabled by default, and unavailable until all listed gates pass. If maintainers define any API-written success on a required check as a bypass regardless of the independent verifier, classify it as `branch_protection_bypass` and stop this implementation path; do not rename or split the action to evade that decision.

This distinction is a policy judgment, not a GitHub guarantee. The public Checks API documents `PATCH /repos/{owner}/{repo}/check-runs/{check_run_id}` for updating a specific run, permits `status: completed` and `conclusion: success`, and requires an App with `checks:write`; it also documents a separate `POST /repos/{owner}/{repo}/check-runs` creation route ([Update a check run](https://docs.github.com/en/rest/checks/runs?apiVersion=2026-03-10), [Checks API guide](https://docs.github.com/en/rest/guides/using-the-rest-api-to-interact-with-checks)). GitHub's protected-branch documentation says required checks must be successful, skipped, or neutral and can restrict accepted updates to a selected GitHub App ([About protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)). The design records that workflow-dispatch checks do not satisfy PR required checks. These API and branch-protection rules do **not** establish that an Actions App token from a later `workflow_dispatch` can update a prior `pull_request` run's Check Run, or that branch protection will accept that cross-run update. Both remain unproven until a separately authorized live pilot.

## Proposed policy and authorization changes for a separate reviewed PR

- Add a canonical `highRiskActions` list to the risk policy with only `stage1_required_check_recovery`. Keep `criticalActions` and its required IDs, including `branch_protection_bypass`, unchanged. In `policy.mjs`, extend exact-key validation, require the fixed high-risk action set with no duplicates or overlap, and load it into the immutable policy. Unknown IDs remain errors.
- In `classify-risk.mjs`, accept this declared action and classify it as high with an explicit matched rule and human-approval requirement; continue classifying every `criticalActions` item as critical. Actions must never default to low/medium or be accepted from caller hints. Add focused parser/classifier tests for missing, duplicate, unknown, overlapping, and valid actions, and prove the critical set still classifies as critical.
- In the trusted host approval boundary (`scripts/loop/github-auth-provider.mjs` and the TTY prompt), require a one-use authenticated approval for this exact capability and exact repository/PR tuple, current tested SHA, one context (`client` or `server`), App ID `15368`, numeric Check Run ID, fixed workflow ID/path/ref/source SHA, request ID, expiry, and reserved CI budget. Derive all target fields from fresh host observations, not caller/workflow inputs. Missing trusted approver configuration, invalid/stale approval, tuple drift, or reused approval refuses before a write. This approval and policy change need their own review; no Phase 1 caller-supplied scope is authorization.
- Preserve `ciRunLimit: 2` and every other stop-condition value. Keep dispatch and publication as distinct least-privilege jobs and credentials: the dispatcher may issue only `POST /repos/{owner}/{repo}/actions/workflows/{fixed_workflow_id}/dispatches` with `ref: main`; the publisher may perform only the required fixed-origin read lookups and one `PATCH /repos/{owner}/{repo}/check-runs/{validated_numeric_id}`.

## Transport boundary and invariants

The publisher must reject arbitrary URLs, redirects, extra methods, and every route other than those reads and that single validated Check Run PATCH. Its request body must preserve the existing name/context and head SHA, set only the completed-success result after verifier success, and attach only a bounded summary/link to the trusted retry run. Do not expose generic request bodies or caller-selected IDs. The `checks:write` permission itself is broader than this one operation: the API also has Check Run creation and re-request, Check Suite creation/re-request, and preference operations. A transport-level method/path allowlist is therefore mandatory. The publisher cannot create a new result because `POST /check-runs` is denied; it cannot edit branch protection because no branch-protection route or credential is allowed; it cannot rerun any workflow because it has no Actions write permission and Actions routes are denied; and it cannot substitute an identity because only the unique prior failed Check Run ID whose context, App ID, SHA, and name are freshly revalidated can be patched. The dispatcher likewise cannot call run/job rerun, cancel, enable/disable, or any other Actions write route.

This boundary reduces selection and route abuse; it does not erase the semantic effect. A successful PATCH intentionally turns the exact required failure into success after the trusted verifier has independently rerun the unchanged check definition on the same SHA. The host must later observe that GitHub recognizes this exact result as satisfying the current required-check rule; a successful API response alone is not completion.

## Fail-closed criteria and evidence still required

Do not dispatch or publish if policy is unmerged, the action is not in the canonical policy, trusted exact approval is unavailable, budgets/state are missing or stale, the PR is a fork or does not target `main`, the tuple/SHA changes, the context or App ID is unsupported, check results are missing/duplicate/incomplete, the selected failure is not the unique current failure, an active/newer run exists, the workflow identity/source SHA is untrusted, verifier definitions differ from normal CI, verification fails/is skipped/cancelled/times out, or any API response is ambiguous. Reserve `ciRunLimit` before dispatch; ambiguous write outcomes consume the reservation and escalate without automatic retry. Never fall back to rerun endpoints or another Check Run.

Before activation, maintainers still need a separate reviewed policy PR and a fresh implementation run; reviewed least-privilege workflow/job graph and source identity; trusted approver, host-managed persisted state and current tuple checks; separately reviewed GitHub App permissions; and a separately authorized non-main pilot using a naturally eligible flaky failure. The pilot must prove that the exact prior Check Run ID can be updated by the later workflow, retain context/App/SHA, and that current branch protection recognizes the result. Re-read branch-protection configuration and required-check identities before the pilot. No artificial check failure, weakened security gate, live write, policy approval, cross-run acceptance, or branch-protection success is claimed here.
