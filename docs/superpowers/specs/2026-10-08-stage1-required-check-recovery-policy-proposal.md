# Stage 1 required-check recovery policy proposal

**Status:** Historical proposal. PR #295 merged the high-risk classification for `stage1_required_check_recovery`; no GitHub App permission, trusted host capability, workflow dispatch, Check Run update, or live pilot is authorized by this document.

## Current policy evidence

The canonical `risk-rules.yml` now declares `highRiskActions: ["stage1_required_check_recovery"]` alongside the fixed `criticalActions`, including `branch_protection_bypass`. PR #295 added exact schema validation and classifies the new action as high risk with human approval; unknown, duplicate, missing, or overlapping actions are rejected. The protected-path policy classifies `.agent/policy/**`, `.github/workflows/**`, and `scripts/loop/**` as high; the stop policy keeps `ciRunLimit: 2`. This policy classification does not itself provide authenticated host approval or make a Stage 1 write executable.

The design and plan propose a trusted `main` workflow that verifies exactly one allowlisted `client` or `server` check definition against the exact current PR SHA, then uses a separate publisher to update the unique original failed Check Run. The existing required context and App identity are retained (Actions App ID `15368`). This is not a neutral report: after independent verification, it intentionally changes the existing required failure to success.

## Rationale for the separately classified high-risk action

PR #295 adopted the distinct action `stage1_required_check_recovery` for the trusted dispatch and later Check Run update. The rationale remains that this is high risk because it changes the outcome used by branch protection, even after an independent verifier runs. It remains human-approved, disabled by default, and unavailable until all listed gates pass. If future policy review concludes that any API-written success is the critical `branch_protection_bypass`, stop this implementation path; do not rename or split the action to evade that decision.

This distinction is a policy judgment, not a GitHub guarantee. The public Checks API documents `PATCH /repos/{owner}/{repo}/check-runs/{check_run_id}` for updating a specific run, permits `status: completed` and `conclusion: success`, and accepts GitHub App user access tokens, GitHub App installation access tokens, and fine-grained personal access tokens, all with Checks repository permission `write`. This design's separate Actions/GitHub App publisher uses an App token with `Checks:write` and excludes PAT credentials; the API's documented PAT support does not change that design choice. The API also documents a separate `POST /repos/{owner}/{repo}/check-runs` creation route ([Update a check run](https://docs.github.com/en/rest/checks/runs?apiVersion=2026-03-10), [Checks API guide](https://docs.github.com/en/rest/guides/using-the-rest-api-to-interact-with-checks)). GitHub's protected-branch documentation says required checks must be successful, skipped, or neutral and can restrict accepted updates to a selected GitHub App ([About protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches)). The design records that workflow-dispatch checks do not satisfy PR required checks. These API and branch-protection rules do **not** establish that an Actions App token from a later `workflow_dispatch` can update a prior `pull_request` run's Check Run, or that branch protection will accept that cross-run update. Both remain unproven until a separately authorized live pilot.

## Policy and authorization status

- **Merged in PR #295:** the canonical `highRiskActions` list contains only `stage1_required_check_recovery`; `criticalActions`, including `branch_protection_bypass`, remains unchanged. The policy loader/classifier validates the fixed set and requires human approval for the high-risk action.
- **Still required for implementation:** the trusted host must require one-use authenticated approval for the exact capability and repository/PR tuple, tested SHA, one context (`client` or `server`), App ID `15368`, numeric Check Run ID, fixed workflow identity, request ID, expiry, and reserved CI budget. Derive targets from fresh host observations. Missing trusted approver configuration, invalid/stale approval, tuple drift, or reused approval must refuse before a write. Caller-supplied Phase 1 scopes are not authorization.
- Preserve `ciRunLimit: 2` and every other stop-condition value. Keep dispatch and publication as distinct least-privilege jobs and credentials: the dispatcher may issue only `POST /repos/{owner}/{repo}/actions/workflows/{fixed_workflow_id}/dispatches` with `ref: main`; the publisher may perform only the required fixed-origin read lookups and one `PATCH /repos/{owner}/{repo}/check-runs/{validated_numeric_id}`.

## Transport boundary and invariants

The publisher must reject arbitrary URLs, redirects, extra methods, and every route other than those reads and that single validated Check Run PATCH. Its request body must preserve the existing name/context and head SHA, set only the completed-success result after verifier success, and attach only a bounded summary/link to the trusted retry run. Do not expose generic request bodies or caller-selected IDs. The `checks:write` permission itself is broader than this one operation: the API also has Check Run creation and re-request, Check Suite creation/re-request, and preference operations. A transport-level method/path allowlist is therefore mandatory. The publisher cannot create a new result because `POST /check-runs` is denied; it cannot edit branch protection because no branch-protection route or credential is allowed; it cannot rerun any workflow because it has no Actions write permission and Actions routes are denied; and it cannot substitute an identity because only the unique prior failed Check Run ID whose context, App ID, SHA, and name are freshly revalidated can be patched. The dispatcher likewise cannot call run/job rerun, cancel, enable/disable, or any other Actions write route.

This boundary reduces selection and route abuse; it does not erase the semantic effect. A successful PATCH intentionally turns the exact required failure into success after the trusted verifier has independently rerun the unchanged check definition on the same SHA. The host must later observe that GitHub recognizes this exact result as satisfying the current required-check rule; a successful API response alone is not completion.

## Fail-closed criteria and evidence still required

Do not dispatch or publish if policy is unmerged, the action is not in the canonical policy, trusted exact approval is unavailable, budgets/state are missing or stale, the PR is a fork or does not target `main`, the tuple/SHA changes, the context or App ID is unsupported, check results are missing/duplicate/incomplete, the selected failure is not the unique current failure, an active/newer run exists, the workflow identity/source SHA is untrusted, verifier definitions differ from normal CI, verification fails/is skipped/cancelled/times out, or any API response is ambiguous. Reserve `ciRunLimit` before dispatch; ambiguous write outcomes consume the reservation and escalate without automatic retry. Never fall back to rerun endpoints or another Check Run.

The high-risk classification is merged in PR #295. Before activation, maintainers still need a fresh implementation run; reviewed least-privilege workflow/job graph and source identity; trusted approver, host-managed persisted state and current tuple checks; separately reviewed GitHub App permissions; and a separately authorized non-main pilot using a naturally eligible flaky failure. The pilot must prove that the exact prior Check Run ID can be updated by the later workflow, retain context/App/SHA, and that current branch protection recognizes the result. Re-read branch-protection configuration and required-check identities before the pilot. No artificial check failure, weakened security gate, live write, App permission grant, cross-run acceptance, or branch-protection success is claimed here.
